# MSF comparison-proof policy

## Назначение

Comparison proof превращает описание модели в короткое проверяемое доказательство: один тип задачи, одинаковые условия, два результата и честный вывод. Его задача — показать зрителю **где модель оказалась сильнее, слабее или где победителя пока нельзя назвать**, а не сымитировать benchmark.

Подход опирается на pairwise comparison: ответы сравнивают бок о бок при скрытом порядке и оценивают по заранее названному критерию. Такой формат применяется Chatbot Arena для human-preference evaluation, но один короткий ролик не должен выдавать единичный пример за глобальный рейтинг.[1][2]

## Два допустимых режима

| Режим | Что можно утверждать | Обязательные условия |
|---|---|---|
| `observed` | Краткий вывод о конкретной задаче: кто выиграл, проиграл или где есть ошибка | Одинаковая задача, условия, критерий, evidence claims и как минимум один воспроизводимый asset/source URL с результатом |
| `proposed` | План честного личного теста; победителя называть нельзя | Одинаковая задача, условия, критерий; итогом является инструкция, а не сравнение фактических результатов |

`observed` proof без источника, снимка результата, исходного файла, публичной страницы или другого разрешённого asset не попадает в storyboard. `proposed` proof не получает визуальный label «победитель».

## Typed contract

Каждый proof содержит:

| Поле | Смысл |
|---|---|
| `comparison_id` | Стабильный идентификатор доказательства |
| `mode` | `observed` или `proposed` |
| `visual_mode` | `code_test`, `ui_build`, `game_build`, `data_viz`, `research_answer`, `incident`, `safety_failure` |
| `task` | Одна пользовательская задача, написанная понятным языком |
| `prompt_summary` | Краткое описание одинакового prompt, без скрытых инструкций и секретов |
| `models` | Две или три сравниваемые модели в нейтральном порядке |
| `conditions` | Что было одинаково: входные данные, инструменты, лимит времени, число попыток и способ оценки |
| `criterion` | Наблюдаемый критерий: «прошли тесты», «страница работает», «график читается», «ответ сослался на источник» |
| `outcome` | `left_wins`, `right_wins`, `tie` или `inconclusive`; для `proposed` только `inconclusive` |
| `strength` и `weakness` | Одно наблюдение о сильной и слабой стороне, привязанное к задаче |
| `evidence_claim_ids` | Claims, подтверждающие факт сравнения |
| `asset_urls` | Разрешённые source/result assets для observed proof |
| `disclosure` | Короткая оговорка о границе вывода: один prompt не измеряет «лучшую модель вообще» |

## Quality gates

1. Одна задача не доказывает общий рейтинг. В каждом ролике требуется disclosure.
2. Название модели не может быть на одной стороне экрана постоянно: порядок сторон случайно/детерминированно чередуется между роликами.
3. Нельзя сравнивать ответы при разных инструментах, разном объёме входных данных или разных лимитах, если это не обозначено в conditions.
4. Нельзя заявлять «дешевле», «доступнее» или «быстрее» без primary/official evidence либо измеренного результата с указанными условиями.
5. `incident` и `safety_failure` требуют проверяемого описания ущерба; нельзя драматизировать гипотетическую ошибку как произошедший случай.
6. Перед render нужен хотя бы один визуальный asset для observed proof. Иначе draft останавливается на текстовом research stage.
7. Visual selection должен соответствовать типу доказательства: `PromptABLab`/`BenchmarkArena` для side-by-side, `AppScreenGallery`/`BeforeAfterLens` для UI и игр, `BrowserDecisionTable`/`DocumentMarginNotes` для research, `EvidenceConflictBoard` для спорного claim, `ColdOpenContradiction` для hook.

## Сценарная последовательность

```
контрастный hook → одинаковая задача → два результата → критерий → честный вывод/слабое место → Telegram asset
```

Начальный тезис должен называть **задачу**, а не только модель. Хорошо: «Обе модели попросили собрать одну страницу — какая оставила меньше ошибок?» Плохо: «Модель X уничтожила модель Y».
